# Live agent discussion and optional office view

Research checked 2026-10-31 against Kepler commit `8fb5088` and upstream repository sources. Recommendation: build a **Research Desk** in the existing React dashboard, with a chronological, live, evidence-linked discussion as the primary surface. Add a small optional office view later, driven by the very same persisted events. It should visualize actual work and actual messages; it must not manufacture conversation, percentage progress, motion implying work, or expose hidden chain of thought. No implementation or dependency installation is implied by this research.

## What Kepler already has

At `8fb5088`, `swingtradev3-dashboard/src/hooks/useDashboardData.ts` fetches cognition runs and reports and connects live events; `src/lib/sse.ts` parses `ready`, `heartbeat`, and execution events; `swingtradev3/api/routes/sse.py` streams durable `execution_events`, supports `after_id` and `Last-Event-ID`, and polls at one-second intervals. Existing cognition queries poll; activity snapshots in `swingtradev3/api/tasks/activity_manager.py` are keyed by agent name and are not a complete run-specific conversation. The current stream defaults to the latest event when no cursor is supplied; it does not by itself supply historical discussion or guarantee atomic event creation with a future research state update. There is no ResearchDesk screen in this revision. Use `git show 8fb5088:<path>` for the exact version; do not confuse it with the current checkout.

## Proposed experience

A run list identifies each independent run, including concurrent instances of the same agent. Selecting a run opens a chronological transcript of **published agent-to-agent messages** and explicit replies, with agent role, time, message type, and links to the precise evidence used. Show actual disagreement and unresolved questions; do not invent a debate when the orchestration emits none. Clearly separate facts, estimates, hypotheses, decisions, and missing evidence. Streaming text is marked partial until finalized; reconnects preserve the finalized transcript. A live status strip shows observed queued, running, waiting, completed, failed, cancelled, or stale/disconnected states; display unknown when no reliable state exists.

Click a message or step to see its actual inputs and outputs, published rationale/summary, relevant tool invocation and result metadata, timestamps, and linked evidence. A source drawer opens original URL or internal artifact, title, publisher, observed/published time, fetch time, excerpt, data version and as-of time, units, and missing/stale/error state. Market facts link to the actual snapshot/version and distinguish delayed data. Broken, unavailable, or unverified sources stay visible with their failure state; no generated citations or unsupported claims. Do not render raw private reasoning, secrets, or unrestricted tool output. Explicitly emitted user-visible messages are the transcript; status labels are not messages.

Optional office: each active actor represents a real `(run_id, step_id, agent_id)` instance; simultaneous instances remain distinct. Position and decorative idle animation must not imply unobserved work, meetings, speaking, or handoffs. A speaking indicator requires an actual message event; click selects the same transcript and source panel. On stale/disconnected state stop presenting activity as current. Motion is optional and reduced-motion friendly. The transcript, status list, and source links work with keyboard, screen reader, and without canvas; provide focus states, text alternatives, color-independent statuses, and restrained live-region announcements. Support narrow screens and paused scrolling without losing events.

## Contract and delivery

Define a versioned Kepler-owned envelope with durable monotonically ordered event ID/cursor, schema version, run ID, step ID, agent instance/role, event type, server timestamp, correlation/causation and message IDs, and visibility. Types should include run/step lifecycle, published message start/delta/final (or finalized message only), evidence attached, and error/cancel. Messages carry sender, optional recipient/reply-to, explicit semantic kind, content, and evidence IDs; evidence records reference immutable/versioned source snapshots with provenance, retrieval/as-of times, excerpts and access/availability state. A final message and its cited evidence must be recoverable after restart. Retain a clear distinction between observed status, emitted message, evidence, and user-visible summary. Deduplicate by event/message identity; keep per-run order and handle concurrent producers.

Commit run/step state and its authoritative event atomically in Postgres, then serve history plus SSE replay by cursor. Snapshot/history and stream handoff must have a consistent watermark so events cannot fall into a gap; reconnect with last applied cursor, handle duplicate delivery, expired cursors and authorization on both history and stream. Extend the existing execution-event stream only if its schema, retention, ordering and access model support this; otherwise provide a dedicated durable research event stream with the same replay pattern. Do not treat a browser socket or in-memory agent snapshots as the source of truth. Stream partial tokens only when the backend truly emits them; specify ordering, finalization, recovery, and how partial chunks are persisted or reconstructed. Query invalidation should target the affected run and source rather than refresh every dashboard query on each token.

ADK events should be translated by an explicit backend adapter into these semantic, approved-to-display records. Codex app-server uses its own [JSON-RPC thread/turn/item protocol](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md); map its lifecycle, message deltas, and tool/approval events into the same Kepler contract if an offline Codex run is displayed. Native JSON-RPC notifications are not already Kepler SSE events, evidence, or durable replay: a server-side bridge must identify threads/turns/items, persist selected events, handle reconnection and failure, and never display internal reasoning as conversation. AG-UI is another optional translation at the boundary; it does not replace this canonical model, and its transport-agnostic events do not automatically provide persistence or exactly-once delivery.

A practical sequence is: (1) persist and replay real messages and evidence for one existing cognition run; (2) build the transcript, source drilldown, error and reconnect states; (3) verify concurrent runs, evidence provenance, duplicate/replay behavior, reduced motion and keyboard access; (4) assess a small office renderer against that same data. If the current agents do not publish inter-agent messages or evidence references, instrument the actual handoffs first and show the resulting absence honestly. Runtime selection follows the mandatory Codex conformance gate in IMPLEMENTATION_PLAN.md and COLLABORATIVE_HARNESS_RESEARCH.md; the UI uses the same canonical contract whether the selected room coordinator is dynamic ADK or Codex App Server.
