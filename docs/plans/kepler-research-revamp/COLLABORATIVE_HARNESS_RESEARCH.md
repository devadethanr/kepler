# Collaborative research harness: decision and implementation contract

Research note, 31 October 2026. This supersedes the fixed sequential debate in IMPLEMENTATION_PLAN §§2, 10, 12 and P4/P6 wherever inconsistent. It does not authorize application changes, installation, inference calls or trading. Baseline: Kepler `origin/main` 8fb50888c47a8b4f62e0917dd0475ee5dfaa6fb0, inspected statically. User intent is unattended collaborative research and manual approval of LIVE entries. This note describes a target, not a tested implementation or evidence of trading performance.

## Decision

Build **one Research Room contract** in the existing Python/Postgres application, with a dynamic ADK-based room as the initial runnable implementation and a time-boxed Codex App Server feasibility gate before selecting a production runtime. The room is an adaptive conversation among agents, not a predetermined thesis/skeptic/rebuttal chain. Reuse existing ADK agents, data services, cognition validators and SSE; replace orchestration rather than duplicate the application. Keep ADK as the single deployed orchestration runtime if the Codex gate fails. If Codex passes every gate below, select the Codex room adapter instead and retire the ADK room coordinator; existing deterministic data and validation functions remain callable services. Do not run both orchestration engines for a single room or maintain two production implementations indefinitely.

Reason: Codex's open source native collaboration, tools and skills are an excellent fit for the user's preferred working style, and App Server gives a real external integration boundary. But the currently running endpoints and two different local model/provider assignments have not been proven to support its actual Responses protocol, tool calls, native children, recovery and strict budgets. An ordinary OpenAI-compatible chat endpoint does not establish that. ADK is already used in Kepler, routes through Python and can implement the same adaptive semantics now. This is a contingency decision, not a claim that either framework is inherently more intelligent. No extra orchestration framework or home-grown Responses shim is justified without measured evidence.

## Room behavior and interface

A run starts with a pinned, as-of evidence bundle, explicit question, source permissions and a shared remaining budget. The chair requests initial independent analysis from at least two relevant roles (for example market/evidence and skeptic); thereafter agents can address one another, challenge a claim, request a permitted evidence lookup, suggest another specialist, revise a view, or ask the chair to synthesize. The chair selects next recipients/actions from current open questions and dissent; a participant may challenge the chair. Roles can return later and address new findings. These are substantive messages citing evidence IDs and uncertainty, not simulated animation or model-private chain of thought. The parent budget and evidence checks are deterministic and outside model authority. Start with at most three active roles and at most one fast and one slow inference concurrently; roles can take turns on the same endpoint. Concurrency is scheduling, not a claim of independent hardware or evidence.

Expose adapter operations `start_room(run_id, question, evidence_snapshot, budget)`, `send_message(run_id, sender, recipients, message_id, reply_to, claim_ids, evidence_ids, content)`, `request_evidence(run_id, query, as_of)`, `finish_room(run_id, conclusion)` and `cancel_room(run_id)`. Messages contain a bounded plain-language public rationale, cited evidence references, stance, unresolved questions and proposed next action; no hidden reasoning required. Messages/tools are subject to schema, length, freshness, citation, injection and permission checks. A validated final conclusion records recommendation/no-action/abstain, facts and citations, hypotheses, dissent, missing information, as-of time and result quality; the existing deterministic portfolio/risk checks and separate user approval remain the only route toward a live entry. No model message mutates an order, position, risk threshold, safety policy or account.

Stop immediately on cancellation, deadline, exhausted global calls/tokens/tool budget, authority violation, unrecoverable provider or persistence failure; mark partial/degraded/abstained with a reason and retain dissent. Otherwise the chair may conclude once each material issue is resolved, explicitly recorded as unresolved, or unavailable after a reasonable targeted lookup. Require at least two substantive participant contributions and a chance for objection before an ordinary conclusion; inadequate evidence or failed participation yields abstention/degraded, never manufactured consensus. Prevent loops with duplicate-message detection, max consecutive messages without new claim/evidence, and a deterministic parent ceiling. Initial full room ceilings: 20 minutes, 24 model calls, 24 tool calls, 100k input and 16k generated tokens inclusive of all children and reasoning; short room 3 minutes, 6 calls and 8 tools, with explicit token caps. These are hard ceilings, not targets or guaranteed accounting from a provider. If usage cannot be measured or reserved conservatively, stop. Resource and execution limits stay outside editable harness material.

## Durable chat and recovery

Postgres is authoritative. A leased `ResearchRun` contains run/trigger/idempotency IDs, evidence versions/as-of, status, result quality, deadline, per-model/tool versions, remaining/reserved budget, cancellation and lease fencing token. Append immutable `RoomMessage` records with run/sequence/message ID, sender, recipients, reply/causal IDs, role, bounded content, claim/evidence refs, timestamps and validation outcome. Record tool requests/results and agent lifecycle as separate typed `ResearchEvent`s with stable IDs, parent IDs, attempts, budget consumption and sanitized artifact references. Persist message/event and outbox item in one transaction; relay via existing SSE with sequence cursor and replay/deduplication. Do not persist every token or assume a framework's own session store provides exactly-once execution. UI shows real participant messages, citations, outstanding objections and completed/failed tool outcomes; never fabricated discussion.

Use idempotent writes, one live fenced lease per room, heartbeat and bounded retries. Persist intent before each external call; after uncertain completion reconcile by request ID where possible, otherwise mark unknown and retry only safe read-only operations under a new attempt and remaining budget. Restart reconstructs from committed events and stable evidence, resumes only when framework state and child status are verified; otherwise explicitly close as interrupted and start a linked attempt, never pretend a full transcript was recovered. Disconnect/reconnect and cancellation must stop child work and reclaim resources; validate this against the chosen runtime. Outbox and run status must not claim completion before durable final artifact validation.

## Local models and Codex gate

The proposed GPUs serve Gemma 4 E4B and Qwen3.5-9B as candidate fast/slow endpoints; actual revision, device, quantization, capacity and endpoint assignments are a local preflight question. These are user-specified candidates, not a claim of measured quality. Preserve working baseline and no paid fallback. Test each model independently and under simultaneous resident load, real tool/structured-output behavior, malformed output, timeouts and cancellation. The room must degrade or abstain when either endpoint is unavailable; no automatic external provider.

Codex feasibility is a bounded, isolated research-only spike against pinned upstream build and local endpoint(s):
1. Verify Responses API requests, streaming events, tool-call/result round trips, errors, cancellation and multi-turn context against each actual server, not just `/v1/chat/completions`; validate schemas and tool-call fidelity with both models. Codex's bundled Responses proxy forwards `/v1/responses`; it is not a Chat Completions translator [C4]. Any adapter must pass the full suite without silently dropping content or tools; do not build an unbounded protocol translation project.
2. Verify configured native multi-agent availability, actual child spawn/message/reply/continuation and parent visibility, including model role routing to both endpoint identities and recovery after process crash. Upstream exposes model overrides conditionally and children inherit the model by default; the source does **not** establish that a child can independently select another local provider/base URL in this setup [C2]. If not proven, do not claim heterogeneous native subagents. Separate top-level Codex threads with externally mediated chat are acceptable only if all other gates pass and this remains one coordinator, not a second swarm framework.
3. Demonstrate complete durable public message/tool event capture, correlation IDs, replay, no missing child activity, cancellation and strict global parent accounting including children. Native transcripts or App Server notifications alone are not a transactional event store. Reject if the host cannot account for or halt child calls before a ceiling is crossed.
4. Demonstrate sandbox and externally enforced network/filesystem/process isolation; restrict to read-only evidence tools and approved inference RPC. No broker credentials, live write APIs, production mounts, arbitrary shell or browser network access. Verify an attempted prohibited action actually fails; model instructions alone are not enforcement. Capture provenance, redact secrets and bound retention.
5. Run representative held-out Kepler tasks against the ADK room baseline: meaningful multi-turn challenge/revision, exact evidence citations, abstention, malformed/tool-error handling, latency and budgets. Select Codex only if it meets correctness, observability and resource gates and improves or is non-inferior on the same tasks; no generic coding score or vote count suffices. Pin version and protocol; a failing gate selects the ADK room, with failure recorded and no hidden cloud fallback.

Codex App Server is a JSON-RPC service with thread and turn lifecycle surfaces [C3]. It is preferable to embedding unstable Rust internals: host Python owns state, policy and event transactions, and talks to an isolated App Server process. The TypeScript SDK wraps the CLI and communicates via JSONL [C5]; introducing Node solely for this Python application provides no demonstrated advantage. App Server is a candidate integration, not proof that all child events or limits are observable. Reuse native collaboration and skills if the above behavior is verified. Adopt tool/skill ideas and existing APIs first; do not copy large internal Rust modules into Python. Codex search/file/shell are coding-oriented capabilities and must be individually disabled or confined to a read-only sanitized evidence workspace; use narrowly scoped read-only evidence search/MCP tools instead of assuming its stock file search understands Kepler data. MCP is a transport, not an authorization boundary.

## Harness² belongs inside the research loop

Harness² proposes, probes and composes harness changes with fixed model weights [H1]. Integrate its task/evaluator concepts into the Room as a separate **research-only improvement job**: room agents can propose a versioned candidate prompt, skill or evidence-retrieval instruction in a disposable candidate directory; independent evaluator runs baseline and candidate against versioned, temporally separated cases; a composer may propose a combined candidate from successful probes. Record each proposal, probe result and composition as room messages/events and preserve rejected candidates. Agents consume the currently approved immutable research harness during real research; they can initiate and review candidate experiments, so Harness² is part of their working process rather than a disconnected lab. It does not mean agents may self-promote changes.

Integration requires a custom Kepler task/evaluator adapter and a proven local executor/protocol; released benchmarks do not establish Kepler performance. No runtime mutation of risk, trade permissions, executable app code, budget caps, network rules, account credentials or promotion gates. Candidates run with sanitized snapshots, no broker/network secrets, no production writable mounts and externally enforced limits. Upstream warns its default executor network is unrestricted and Codex sandbox disabled [H1]; never adopt those defaults. Development -> independently held-out temporal replay -> shadow/paper -> manual promotion of immutable version -> rollback pointer. Citation fabrication, authority violations or evidence leakage reject regardless of aggregate score; compare grounding, abstention, completion and cost/latency, not model self-praise or one PnL backtest. Weights do not change.

## Practical rollout and reuse

P1: implement transactional runs, messages, outbox, fencing, shared budget and read-only evidence contract using existing Python services. P2: implement dynamic ADK room atop current specialists and model router; retire fixed stage dispatch for this path, retaining deterministic checks. P3: execute isolated Codex feasibility and model tests on actual hardware; choose exactly one room runtime using the gate above. P4: add Harness² candidate/probe/compose integration and a truthful room UI; initially shadow research, then scheduled autonomous research when recovery, source-quality and budget tests pass. Manual LIVE entry approval stays in force throughout. Existing news ingestion, cognition reports, SSE and model clients should be extended, not replaced; current `agents/research/pipeline.py` imports `SequentialAgent`, while `api/routes/scan.py` uses in-memory ADK sessions, which need migration rather than being represented as durable chat.

Acceptance: test non-scripted back-and-forth that changes an agent's position on cited new evidence; preserve unresolved disagreement; prove duplicate events, crash/restart, provider outage, incomplete usage, deadline, prompt injection, invalid citation and cancellation behavior. Under identical replay, do not exceed execution-loop latency and hard risk deadlines specified in the existing plan. A run with two agreeing models is not independent corroboration; compare claims to versioned sources. Measure usefulness prospectively, without promising alpha.
